# FastAPI, uv, and Docker

## 1. Purpose

This project demonstrates, in a minimal form, the packaging of a FastAPI web
application into a Docker image. Dependency management is performed with uv:
the files `pyproject.toml` and `uv.lock` replace `requirements.txt`. The
project additionally demonstrates a file based approach to secret management.
An authentication token required by the application is attached to the
container at runtime and is never embedded into the image and never passed
through environment variables.

The application stores its data in memory. All data are lost when the
container is removed. This behaviour is intentional: it demonstrates the
ephemerality of containers.


## 2. Project structure

```text
student-api/
├── app/
│   ├── __init__.py      # empty file; makes "app" a Python package
│   └── main.py          # the FastAPI application
├── secrets/             # the secret token; excluded from git and from the image
│   └── grade_token
├── .dockerignore        # files excluded from the build context
├── .gitignore
├── .python-version      # pins the Python version for uv
├── Dockerfile
├── pyproject.toml       # project metadata and dependencies
├── uv.lock              # exact pinned versions; generated by uv, committed
└── README.md
```

The file `uv.lock` must exist and be committed before the image is built:
the Dockerfile executes `uv sync --frozen`, which installs exactly the locked
versions and does not resolve dependencies anew.

## 3. Prerequisites

- uv: `curl -LsSf https://astral.sh/uv/install.sh | sh`
- Docker

## 4. Authorization model

All read operations of the API are public. The modification of a grade is
restricted: the request must contain the header `X-Grade-Token` whose value
equals a secret token, referred to below as the dean's seal.

The application reads the token from a file. The default path follows the
Docker convention for secrets: `/run/secrets/grade_token`. For local
development the path may be overridden with the environment variable
`GRADE_TOKEN_FILE`.

If the file is absent, the application terminates during startup. This
behaviour, known as fail fast, ensures that a container without the secret
never serves requests.

## 5. Preparation of the secret

```bash
mkdir -p secrets
python3 -c "import secrets; print(secrets.token_urlsafe(32))" > secrets/grade_token
chmod 600 secrets/grade_token
```

The standard library module `secrets` is intended precisely for the
generation of cryptographic tokens.

The directory `secrets/` is listed in `.gitignore` and in `.dockerignore`.
The latter requires particular attention: during `docker build` the entire
build context is transmitted to the Docker daemon. Exclusion of the directory
guarantees that the secret never leaves the host machine, independently of
the contents of the Dockerfile.

## 6. Local execution without Docker

```bash
uv sync
GRADE_TOKEN_FILE=./secrets/grade_token uv run uvicorn app.main:app --reload
```

The interactive documentation is available at <http://127.0.0.1:8000/docs>.

## 7. Construction of the image

```bash
docker build -t student-api .
```

The output of the command marks reused layers with the word `CACHED`. The
Dockerfile copies `pyproject.toml` and `uv.lock` before the source code;
consequently, an edit of the application code does not invalidate the layer
in which dependencies are installed.

## 8. Execution of the container

```bash
docker run --rm -p 8000:8000 --name student-api \
  -v "$(pwd)/secrets/grade_token:/run/secrets/grade_token:ro" \
  student-api
```

| Option | Meaning |
|---|---|
| `-p 8000:8000` | forwarding of host port 8000 to container port 8000 |
| `--name` | a readable name for `docker stop` and `docker logs` |
| `--rm` | removal of the container upon termination |
| `-v …:/run/secrets/grade_token:ro` | mounting of the secret file at the conventional path; the `ro` flag forbids modification from within the container |

The Dockerfile requires no modification for the distribution of the secret:
the token is attached at runtime and does not form part of the image.

## 9. Interaction with the API

```bash
curl http://localhost:8000/
curl http://localhost:8000/students
curl http://localhost:8000/students/1

curl -X POST http://localhost:8000/students \
     -H "Content-Type: application/json" \
     -d '{"id": 2, "name": "Bob", "course": "DevOps"}'

curl -X PATCH http://localhost:8000/students/1 \
     -H "Content-Type: application/json" \
     -H "X-Grade-Token: $(cat secrets/grade_token)" \
     -d '{"grade": 100}'
```

## 10. Security analysis

### 10.1 Environment variables as an insecure channel

The following invocation is deliberately incorrect and serves as a
demonstration:

```bash
docker run -d --name env-demo -p 8000:8000 \
  -e GRADE_TOKEN=demo-token student-api
```

Two observations follow.

First, the container terminates shortly after startup: the application
expects a file and refuses to operate with an environment variable. This is
the intended fail fast behaviour.

Second, the value of the variable remains fully accessible to any observer
of the host even though the application never read it:

```bash
docker inspect env-demo --format '{{range .Config.Env}}{{println .}}{{end}}' | grep GRADE
```

The output contains the token in plain text. The command line itself also
remains in the history of the shell.

The conclusion is general: environment variables form part of the
configuration of a container and must be treated as publicly observable
data. They are inherited by every child process and are recorded by
diagnostic and logging tools.

```bash
docker rm env-demo
```

### 10.2 Verification of the file based mechanism

With the correct invocation of section 9, the same inspection reveals only
the mount, not the content:

```bash
docker inspect student-api --format '{{json .Mounts}}'
```

The output contains the source path on the host, the destination path in the
container, and the flag `RW: false`.

The behaviour of the protected endpoint is as follows:

| Request | Result |
|---|---|
| without the header `X-Grade-Token` | 422; the header is required |
| with an incorrect token | 403; the token does not match |
| with the correct token | 200; the grade is modified |

### 10.3 Rotation of the secret

The application reads the file on every request. Rotation therefore requires
no restart of the container:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))" > secrets/grade_token
```

Requests with the previous token now receive the response 403; requests with
the new token succeed.

A note on file replacement: the file must be overwritten in place, which the
shell operator `>` performs. Certain editors replace the file atomically,
which creates a new inode; the container then continues to observe the
previous content through the bind mount.

## 11. Design principles

- The secret is a file at a fixed path. This interface is uniform across
  `docker run`, Docker Compose, Swarm mode and Kubernetes.
- The secret is attached at runtime and is not included in the image. Images
  are intended for distribution through registries and must not contain
  credentials.
- Access to the file is restricted: the mount is read only, the file
  permissions are 600, and the directory is excluded from version control
  and from the build context.
- The application verifies the presence of the secret during startup and
  terminates if it is absent.
- Comparison of tokens is performed with `hmac.compare_digest`, which
  prevents timing attacks.
- The file is read on every request, which enables rotation without
  interruption of service.

## 13. Extension to Docker Compose

The application code requires no changes under Compose, because the path
convention is identical:

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password

secrets:
  db_password:
    file: ./secrets/db_password
```

The top level `secrets` section defines the secret; the service level
`secrets` section mounts it into the container. The variable
`POSTGRES_PASSWORD_FILE` illustrates that official images follow the same
file based pattern.
